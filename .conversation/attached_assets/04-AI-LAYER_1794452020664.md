# AI layer — discovery proposal

## Desired experience
Founder preference: a companion character accessible across Chunked. Users can type, and eventually speak, to it. The character is a presentation choice; it does not require 3D, voice or its own AI model.

The AI should serve an approved user problem, not justify collecting every piece of user data.

## Candidate AI jobs
| Job | Minimum context | Proposed result |
| --- | --- | --- |
| Break down a task | Selected task and relevant constraints | Editable small steps |
| Help plan a chunk | Selected chunk, available time, chosen tasks | Suggested manageable plan |
| Help a blocked focus | Focus, next step and voluntary readiness note | Clarifying question or next action |
| Discuss a reflection | Selected reflection and permitted context | Supportive response |
| Explain activity patterns | Relevant calculated aggregates | Qualified explanation and suggestion |

These are options. Choose one or two for the initial experiment.

## Data/context policy
- Send only context relevant to the approved job.
- Explain what data is used and offer control over personal reflections.
- Do not send passwords, payment secrets, unrelated users' records or unnecessary identity.
- Recheck ownership in Laravel for every record fetched by an AI tool.
- Onboarding preferences guide style, not permanent judgments about a person.
- Decide retention and deletion for conversation text.
- Voice audio storage is not required by the draft ERD. Prefer an explicit retention decision over storing recordings by default.

## Interaction and actions
Separate conversation/suggestions from execution.
AI may propose a task or reschedule, but it cannot apply changes directly through free text.
Present the concrete proposed change, obtain confirmation, then validate and authorize on the backend.
Initial AI can be read-only and still be useful.
Draft tool candidates: get_selected_chunk, get_task, summarize_activity, propose_task_steps.
Actual write tools are later, narrowly scoped and audited as needed.
Treat user-authored content as data, not instructions that override system/tool permissions.

## Reliability
- Keep DAY/GROW/FOCUS usable if AI is unavailable.
- Distinguish loading, streaming, failed, canceled and complete states.
- Support retry without duplicating messages or actions.
- Avoid claiming it changed a record before the backend confirms.
- Handle stale context: the task may have changed since the conversation began.
- Avoid representing uncertain insights as factual causes.
- Keep provider/model selection configurable rather than scattered across React.
- Choose limits for usage, context length, timeouts and spend before release.
- Explain when limits apply without inventing premium claims.

## Voice and character
Text first is a working recommendation.
Later voice pipeline could involve speech recognition, reasoning and speech output; provider and latency tradeoffs are open.
Explicit microphone permission and visible listening state are necessary.
Offer mute, hide, keyboard access, readable transcripts and reduced motion.
Character states: idle, listening, thinking, speaking, brief celebration.
Three.js is optional and should follow testing of usefulness/performance; 2D is valid.
Laravel Boost assists development and is separate from this end-user AI layer.

## Evaluation before release
Use representative English/Arabic examples and difficult cases:
- Unrealistic plan given the chunk's available time.
- User requests changing another person's task.
- AI proposes a destructive or unconfirmed change.
- No activity data exists.
- Reflection contains instructions to bypass permissions.
- Provider is slow, unavailable, or returns invalid structure.
- User changes language, revokes context access, or cancels voice.
Check usefulness, factual grounding, tone, confirmation behavior, latency and actual cost.
No provider, budget, success threshold or live integration is approved yet.
