# ERD review notes

## Status and source
07-DRAFT-ERD.dbml reconstructs the 19-entity proposal from our discussions. It is not a database migration or a final checked copy of the Miro board.
The later session correction is included: sessions link to user + required chunk, NOT focus_choices.
No changes to the actual app database have been made.

## Relationships
- users 1 : 0..1 user_settings — has.
- users 1 : 0..1 day_structures — configures.
- themes 1 : 0..N user_settings; a settings row has 0..1 selected theme.
- users 1 : 0..N tasks/goals/habits/focus_choices/focus_sessions/reflections/onboarding_answers/ai_conversations/subscriptions.
- day_structures 1 : 0..N chunks — contains.
- chunks 1 : 0..N tasks; task's chunk is optional.
- goals 1 : 0..N tasks/habits/focus_choices; each link to a goal is optional.
- habits 1 : 0..N habit_logs.
- focus_choices 1 : 0..N focus_checkins.
- chunks 1 : 0..N focus_sessions; session's chunk is REQUIRED.
- reflections 1 : 0..N ai_conversations; conversation's reflection is optional.
- ai_conversations 1 : 0..N ai_messages.
- plans 1 : 0..N subscriptions.
- subscriptions 1 : 0..N transactions.

With simple 1/N labels, place 1 by the parent and N by the referencing child. Each FK is stored in the child. Optionality is separate from maximum cardinality.

## Current draft inventory
users, user_settings, day_structures, chunks, tasks, goals, habits, habit_logs, focus_choices, focus_checkins, focus_sessions, reflections, onboarding_answers, ai_conversations, ai_messages, themes, plans, subscriptions, transactions.

## DBML conventions
Not-null is explicit for required fields; nullable fields omit it.
Enum types describe candidate values.
PK/FK structure and uniqueness are represented.
Dates/timestamps have semantic notes where needed.
The file does not prescribe engine-specific enum migrations or cascading deletion rules.
The draft omits timestamps on static themes and omits updated_at on immutable AI messages as optional MVP simplifications. Other tables retain both timestamps. Review whether theme/message editing is required.
New focus records default to paused in this draft so creating a record does not silently activate a second focus. Activation is a separate controlled operation. Field sizes and these defaults are engineering proposals.

## Open modeling choices — must review before migrations
1. Keep focus_checkins history or store current readiness on focus_choices? Selecting the latter reduces the inventory to 18 tables.
2. Session duration_seconds is included as a proposal because timers pause; define completed versus abandoned state and manual logging before implementing.
3. Chunk configuration edits must not reassign/erase historical activity. The 19-table draft is not a complete schedule-versioning solution.
4. Prayer-based mode needs a decision on manual versus calculated times and the required location/calculation settings. These are intentionally not invented as settled attributes.
5. Simple subscription timestamps/statuses may be insufficient for chosen provider billing, scheduled cancellation and refunds. Finalize payment behavior before claiming production readiness.
6. The transactions status "refunded" only expresses a simple whole-payment state; partial refunds or multiple refund events would need additional modeling.
7. AI usage/cost controls may require a usage ledger or provider-backed metering. ai_messages alone is not a complete quota system.
8. A multi-turn reflection discussion can share one conversation. Whether multiple conversations per reflection are useful is a product choice.
9. Onboarding question text/options currently live in code keyed by question_key; add a questions table only if editable questions are actually needed.
10. Habit schedules and goal progress need defined historical semantics. Do not promise accurate historical streaks from mutable schedules without a policy.
11. Future subtasks, milestones or card-specific steps are not modeled. Determine whether those are real requirements rather than adding tables speculatively.
12. Decide retention, account deletion and FK deletion actions deliberately.

## Constraints outside simple foreign keys
- One active focus per user.
- One active subscription per user.
- Linked personal records have the same owner.
- Nonnegative money/duration; end instant cannot precede start.
- Correct local date semantics.
- Duplicate timer/manual logs do not inflate session counts.
- Backend sets registration role and verifies payment results.
- UI card grouping does not require its own entity.

## Not part of the product ERD
Laravel sessions, password_reset_tokens, migrations, cache and queue infrastructure may be created by the framework.
No templates, community, orders or order_items tables are proposed.
No standalone tables are required for dashboard, current chunk, cart, character animations or calculated insights.
